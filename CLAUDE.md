# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A stock symbol maintenance app for US markets (NASDAQ/NYSE/AMEX/OTC): a plain Node.js/Express backend, a no-build-step vanilla HTML/CSS/JS frontend, and PostgreSQL storage. Its purpose is upkeep of a symbol/company-name/market list — manual CRUD, bulk import, and automated drift-checking against Yahoo Finance — not trading or price data.

## Commands

```bash
npm install
npm start          # node server.js
npm run dev         # node --watch server.js
```

No test suite or lint script is configured.

The app is developed and run inside WSL (Linux), even though the project directory is on the Windows filesystem (`/mnt/c/Users/...` from WSL). Run all `node`/`npm`/`psql` commands from a WSL shell, not PowerShell.

### Database

`sql/schema.sql` is the single source of truth for the schema and is written to be safely re-run after any change (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS` + re-add) — there is no migration framework, just re-apply this file:

```bash
psql -h localhost -U <role> -d <db> -f sql/schema.sql
```

PostgreSQL runs locally in WSL. The app connects over TCP (`localhost:5432`) with password auth via a dedicated role, not the `postgres` superuser and not peer auth — connection settings come from `.env` (see `.env.example`), read by `db.js`. `.env` also holds `SEC_EDGAR_CONTACT`, used only by `scripts/fill-cusip.js` (see below) as the required contact info in its SEC EDGAR requests' `User-Agent`.

### Git

The repo's `origin` is https://github.com/victor5566/update_stock_app (branch `main`). Pushes are done from a Windows-side shell (PowerShell), not WSL — the WSL environment has no GitHub credentials configured, but Windows git already has a cached credential for this account via Git Credential Manager.

## Architecture

**`stocks`** is the core table (`stock_symbol` UNIQUE, `company_name`, `exchange` free text — no longer a 4-value CHECK, `source` CHECK'd to `manual | yahoo | excel_import | nasdaq_trader`), plus extended company-info columns: `isdelisted` (bool, default false), `category`, `cusips`, `sector`, `industry`, `currency`, `company_location`, `urll`, `description`, `ceo`. These are all nullable and optional, and deliberately **not** part of the web add/edit form itself (which only ever *submits* `stock_symbol`/`company_name`/`exchange`, unchanged from before) — but a manual add now auto-fills them a moment later; see the `POST /api/stocks` note below. `category` has no automated source anywhere and is manual/DB-only. Five auxiliary tables hang off `stocks`:
- `company_name_history` / `stock_symbol_history` — append-only audit log of renames, written transactionally, `stock_id` FK `ON DELETE CASCADE` (history disappears if the stock is later deleted).
- `stock_update_candidates` / `stock_removal_candidates` — a snapshot, not a log: `scripts/check-stock-status.js` `TRUNCATE`s and fully repopulates both on every run. Also `ON DELETE CASCADE`, so deleting a stock that happens to be a removal candidate silently drops it from that list too.
- `stock_deletion_log` — the one exception: **no FK to `stocks`**, by design, since these rows must outlive the stock they describe.

**Two transactional diff-and-log mechanisms are the core non-obvious pattern**:
- **Updates**: `lib/applyStockUpdate.js` holds the shared core — `SELECT ... FOR UPDATE`s the current row, applies the update, diffs old vs. new `company_name`/`stock_symbol`, and conditionally inserts into the two history tables. It expects to run inside a transaction the *caller* owns (`BEGIN`/`COMMIT`/`ROLLBACK` + `client.connect`/`release`). Two callers use it: `PUT /api/stocks/:id` (one stock, from the web form) and `scripts/apply-update-candidates.js` (bulk, one candidate row at a time from `stock_update_candidates`). If you add a third way to update a stock, call this instead of re-inlining the diff logic.
- **Deletes**: `DELETE /api/stocks/:id` (`routes/stocks.js`) deletes the row (`RETURNING` its data) and inserts that data into `stock_deletion_log`, in the same transaction. Not yet extracted to `lib/` since there's only one caller.

Any future change to how stocks are updated or deleted needs to preserve these steps, since they're the only thing populating the history/log tables. Both paths sanitize text through a `Buffer.from(str,'utf8').toString('utf8')` round-trip before writing history rows — accented company names (Latin American ADRs, etc.) have tripped a node-postgres encoding edge case here before.

**`source` tracks provenance**, not just for record-keeping: the "manual add log" UI section is literally `GET /api/stocks?source=manual`. Only `POST /api/stocks` (the web form) sets `source='manual'`; each of the import scripts stamps its own source value. If you add a new way to insert stocks, make sure it sets `source` correctly or it will silently pollute the manual-add log.

**Routes** (`routes/*.js`) are each mounted in `server.js` under their own path prefix (`/api/stocks`, `/api/company-name-history`, `/api/stock-symbol-history`, `/api/removal-candidates`, `/api/stock-deletion-log`). `routes/stocks.js` also owns `GET /api/stocks/by-symbol/:symbol`, used by every lookup-before-edit flow on the frontend (rename / change-symbol / delete-by-symbol forms all use a text input + shared `#stock-datalist` autocomplete, deliberately not a `<select>`, per prior feedback in this project). `GET /api/stocks/:id` (numeric id only) returns the full row including the extended detail columns. `PUT`/`POST` on `routes/stocks.js` will accept the extended detail fields in the request body if given, but nothing in the frontend currently sends them - that path exists for completeness, not because anything calls it that way today.

**`POST /api/stocks` auto-fills extended details in the background.** When a manual add doesn't itself specify any of the extended detail fields (the normal case - the web form never does), `routes/stocks.js` responds with the newly-inserted row immediately (so the add stays fast/synchronous) and *then*, fire-and-forget via `autoFillNewStock()`, kicks off `lib/fillCompanyDetails.js` and `lib/cusipLookup.js` concurrently (`Promise.allSettled`, so one failing doesn't block the other) to fetch and write in the same data the bulk scripts would have produced by hand. Errors are only `console.error`'d on the server, never surfaced to the client - a failed auto-fill just leaves those columns `null`, exactly as if the script hadn't been run yet, and `scripts/fill-company-details.js`/`scripts/fill-cusip.js` (which both select "still-missing" rows by default) will pick it up on their next run regardless. If you add a bulk-insert path (an import script, say) that should get this same treatment, call `autoFillNewStock`-equivalent logic per row deliberately - don't let a bulk loop fire hundreds of these concurrently, since `lib/cusipLookup.js` hits two rate-limited external services.

**`lib/yahoo.js`** centralizes the `yahoo-finance2` client. `lookupStock(symbol)` returns `stock_symbol`/`company_name`/`exchange` (now Yahoo's `fullExchangeName`, a free-text string — `EXCHANGE_TO_MARKET` is kept only as a fallback label, not a validation gate) plus best-effort extended fields from `fetchCompanyDetails()` (`sector`, `industry`, `currency`, `company_location`, `urll`, `description`, `ceo` — via `quoteSummary`'s `assetProfile`/`price` modules; `ceo` is picked from `companyOfficers` by matching a "CEO"/"Chief Executive" title; `company_location` is a full postal address composed from `assetProfile`'s `address1`/`address2`/`city`/`state`/`zip`/`country` - not just the country - via the module-local `composeAddress()`, which skips any piece that's missing, since non-US addresses usually have no `state`). `fetchCompanyDetails` never throws — a `quoteSummary` failure (e.g. for non-equity types) just leaves those fields `null` rather than failing the whole lookup. Yahoo doesn't expose CUSIP via these modules at all (it's licensed data from CUSIP Global Services, not something free financial APIs generally redistribute - OpenFIGI deliberately excludes it too).

**`fetchCompanyDetails(symbol, companyName)`'s foreign-listing fallback**: many thinly-traded US OTC tickers are actually a foreign company's secondary/cross-listing - e.g. `ULUCF` (Roland Mineral Enterprises Corp., OTC Pink) has nothing under that ticker on Yahoo at all, but the same company trades as `RME.V` on the TSX Venture Exchange, which Yahoo has full data for. So when the direct `quoteSummary(symbol)` lookup comes back completely empty (and `companyName` was given - not every call site has one), `findAlternateSymbol()` calls Yahoo's `yf.search(companyName)`, takes the top `EQUITY` result, and requires its name to match `companyName` via `lib/normalizeCompanyName.js`'s `companyNamesMatch()` (which strips punctuation/legal-suffix noise) before trusting it - a loose or absent match is treated as "not found," never a guess. Only company details use this fallback; CUSIP lookup (`lib/cusipLookup.js`) doesn't, since it's tied to a specific filing/page for the original ticker, not the company generally.

**`lib/fillCompanyDetails.js`** wraps `fetchCompanyDetails` + the `UPDATE stocks SET sector = ..., ...` write (sanitizing text fields first - see `lib/sanitizeText.js` below) into one `fillCompanyDetails(pool, stock)` call, returning whether anything was written. Shared by `scripts/fill-company-details.js` (bulk backfill) and the `POST /api/stocks` auto-fill above, so the two paths can't drift.

**`lib/cusipLookup.js`** holds the SEC-EDGAR-then-quantumonline.com CUSIP lookup (see `scripts/fill-cusip.js` below for the source details) behind one `lookupCusip(symbol, { onSourceError })` call returning `{ cusip, source }`. It caches the SEC ticker→CIK map for the life of the process (an ~800KB file, no need to refetch per symbol). Shared by `scripts/fill-cusip.js` and the `POST /api/stocks` auto-fill above.

**`lib/validateCusip.js`** implements the real CUSIP check-digit algorithm (`isValidCusip(value)`) - a 9-character CUSIP's last character is a check digit computable from the first 8, so this catches typos without needing to look anything up externally. `routes/stocks.js` calls it to reject a malformed `cusips` value on `POST`/`PUT` with a 400; `lib/cusipLookup.js` calls it to sanity-check whatever either source's page parsing produced before returning it.

**`lib/sanitizeText.js`** is the `Buffer.from(str,'utf8').toString('utf8')` round-trip that turns invalid/unpaired UTF-16 (occasionally seen in text from external APIs) into valid UTF-8 before it hits Postgres, which otherwise rejects the whole `INSERT`/`UPDATE` with "invalid byte sequence for encoding". Shared by `lib/applyStockUpdate.js`, `scripts/check-stock-status.js`, and `lib/fillCompanyDetails.js` - this exact bug silently ate 267 stocks' worth of Yahoo data during initial development of the auto-fill/backfill scripts (they wrote no sanitization at first) before being caught and fixed, so don't skip it when adding a new write path for API-sourced text.

**`lib/normalizeCompanyName.js`** vs. **`lib/cleanSecurityName.js`** solve two different problems and are not interchangeable:
- `normalizeCompanyName` collapses a name to a lossy comparison fingerprint (strips noise words, then *all* whitespace) — used only by the status checker to decide whether two names are "the same" (e.g. NASDAQ Trader's "JP Morgan Chase & Co. Common Stock" vs. Yahoo's "JPMorgan Chase & Co." must compare equal).
- `cleanSecurityName` produces a real display name by stripping the trailing security-type descriptor (" Common Stock", " - Class A Ordinary Shares", " Depositary Shares, each representing...", etc.) while keeping normal spacing — used when *writing* `company_name` (`scripts/import-nasdaq-trader.js` and the one-off `scripts/clean-company-names.js`), not for comparison.

**`scripts/`** are standalone maintenance tools that talk to Postgres directly (each does its own `require('../db')` + `dotenv.config()`) and are meant to be run from the CLI, independent of the running server — not exposed through the web UI or API by design:
- `add-from-yahoo.js SYMBOL...` — look up and insert specific symbols.
- `import-from-excel.js <path.xlsx>` — bulk import from a spreadsheet (header aliases are matched loosely; later duplicate rows for the same symbol win).
- `import-nasdaq-trader.js` — downloads NASDAQ Trader's official listing files and bulk-inserts all NASDAQ/NYSE/AMEX securities, cleaning names via `cleanSecurityName` on the way in. Does **not** cover OTC (that data isn't in an exchange-listing feed); OTC coverage currently comes only from Excel imports.
- `clean-company-names.js` — one-off backfill that re-runs `cleanSecurityName` over every existing row and updates `company_name` where it changed. Does **not** touch `company_name_history` — this is a data-quality fix, not a rename, so it shouldn't show up as one.
- `check-stock-status.js` — batches all DB symbols through `yf.quote()` (200 at a time) and rebuilds the two candidate tables (`TRUNCATE` + full repopulate, so it's always a fresh snapshot, not additive). Pass `{}, { validateResult: false }` as `yf.quote()`'s 3rd arg, or one malformed instrument in a batch of 200 silently drops the entire batch. Update candidates use reason `exchange_mismatch` (was `market_mismatch`) or `company_name_mismatch`; removal candidates use `not_found_on_yahoo` or `no_longer_equity` only — `unsupported_exchange` no longer exists as a reason since `exchange` is free text now, so nothing is "unsupported". Re-run this after any bulk company-name cleanup, since messy names inflate false-positive `company_name_mismatch` candidates.
- `apply-update-candidates.js` — reads every row out of `stock_update_candidates` and applies it to `stocks` via `applyStockUpdate` (so it still gets logged to history), then deletes the row it just applied. Only touches `stock_update_candidates`; `stock_removal_candidates` is intentionally left alone since deleting stocks is a separate, more consequential decision the UI leaves to a human.
- `fill-company-details.js [SYMBOL...]` — backfills the extended detail columns via `lib/fillCompanyDetails.js` (see above). With symbols given, only those; with none, every stock where `sector IS NULL` (a proxy for "never backfilled") - a fresh manual add auto-fills this itself now (see the `POST /api/stocks` note above), so this script is mainly for catching whatever that auto-fill missed the first time (Yahoo having nothing that moment, a transient error, etc.) or backfilling stocks inserted by something other than the web form.
- `fill-cusip.js [SYMBOL...]` — the one exception to "everything talks to Yahoo or NASDAQ Trader": CUSIP isn't in Yahoo's API or NASDAQ Trader's listing files at all, so this uses `lib/cusipLookup.js` (see above), which tries two sources per symbol, in order:
  1. **SEC EDGAR** — every Schedule 13G/13G-A filed about a company prints "CUSIP No. ..." on its cover page, official U.S. government data with zero licensing ambiguity. Maps ticker → CIK via SEC's own `company_tickers.json`, lists that CIK's `SC 13G` filings via `browse-edgar`'s atom output, takes the most recent accession's full-submission `.txt`, and regexes out the CUSIP (normalizing `&nbsp;`/`&#160;` and stripped tags first, since different filers format the cover page differently - this is exactly what caught a real bug during development, where MSFT's filing used `&#160;` and silently fell through to source 2 until the regex was fixed). **Requires `SEC_EDGAR_CONTACT` in `.env`** (a real, identifiable email) - SEC 403s every automated request without one in the `User-Agent`, per https://www.sec.gov/os/webmaster-faq#developers; ask the user before hardcoding a value here, since it's their contact info going to a third party on every request. Not every company has a 13G on file (nothing has crossed the 5% institutional-ownership threshold), so this misses some symbols - that's expected, not a bug.
  2. **quantumonline.com** — a free public securities-lookup site (`search.cfm?tickersymbol=<symbol>&sopt=symbol`), used as the fallback for whatever SEC didn't have. No bulk API, and per its `robots.txt`/pages checked, no terms explicitly barring this, but it's still a small site - `QOL_DELAY_MS` (default 500ms) paces requests between symbols; don't lower it for bulk runs.

  With symbols given, only those; with none, every stock where `cusips IS NULL`.
- `export-to-csv.js` — dumps the full `stocks` table (including the extended detail columns) to `exports/stocks.csv` (committed to the repo, not gitignored). Re-run and re-commit after any bulk data change if you want the export to stay current; nothing does this automatically.

**Frontend** (`public/`) is a multi-page no-bundler setup: `index.html` + `app.js` is the main maintenance UI, and `stock.html` + `stock.js` is a separate, standalone per-stock detail page. Notable patterns to follow if extending it:
- i18n is a `TRANSLATIONS` object (zh/en) applied via `data-i18n` / `data-i18n-placeholder` attributes and a `t()` lookup — not a library. `stock.js` keeps its own small copy of this pattern rather than sharing `app.js`'s object, consistent with this codebase's general preference for per-page duplication over shared abstraction.
- Every list section (stock list, company-name history, symbol history, manual-add log, removal candidates, deletion log — 6 total) paginates client-side at `PAGE_SIZE = 15`, each with its own page-state variable and render function, duplicated per-section rather than abstracted into a shared helper. The two history API endpoints used to `LIMIT 200`; that cap was removed once pagination existed, so don't re-add a server-side limit without also handling it client-side.
- The three lookup-before-edit forms (rename, change-symbol, delete) each follow the same shape: a symbol input with datalist autocomplete, a "查詢/Lookup" button that `GET`s `by-symbol` and disables/enables the rest of the form, a "清空/Clear" button that calls that form's `reset*Form()`, and a submit that does the actual `PUT`/`DELETE`. Copy this shape rather than inventing a new one if adding a fourth.
- Stock-symbol inputs use `class="uppercase"` (CSS `text-transform`, display-only) rather than mutating the input value on keystroke.
- The add/edit form (`#stock-form`) is unchanged from before this app grew the extended detail columns: it still only has `stock_symbol`/`company_name`/`exchange` (the last now a free-text input with an `#exchange-datalist` built client-side from distinct values already in the list, replacing the old 4-option `<select>`). It deliberately does **not** expose the extended detail fields as inputs - the server auto-fills them a moment after a manual add instead (see the `POST /api/stocks` note above), so a freshly-added stock's `/<symbol>` detail page fills itself in within a second or two of adding it, with no separate step needed.
- **Per-stock detail page**: clicking a stock's symbol in the list (`public/app.js`'s `renderTable`) is a plain `<a href="/<lowercase-symbol>">`, e.g. `/aapl` - a real, bookmarkable/shareable URL, not a JS modal. `server.js` serves this via a catch-all `app.get(/^\/[A-Za-z.-]{1,50}$/, ...)` (placed after `express.static` and the `/api/*` routes, so it only fires when no static file matched, and its regex - one path segment, no slashes - can't shadow `/api/*`) that always returns `public/stock.html`. That page's `stock.js` reads the symbol straight from `location.pathname`, calls `GET /api/stocks/by-symbol/:symbol`, and renders the full company-info record read-only, or a "not found" message on 404. It doesn't auto-refresh, so if you land on it immediately after adding the stock (before the background auto-fill lands), you'll need to reload to see the filled-in fields.
